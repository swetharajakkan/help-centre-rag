**Who wrote it:** Support Ops, not us — `ticket-history` 1.3.0 per its own `initialize` serverInfo; we read the source once (`week9/servers/ticket_history/server.py`), but the URL serves whatever they deploy next, with no pinned version, signature or change notice, and its tool descriptions and `instructions` are text from another team that lands straight in our model's prompt.
**What it can reach:** every ticket in its store, not only the one being asked about — including customer name, account id and `contact_email` (PII our answers never need); its tools are read-only (`readOnlyHint`), but every ticket `message` it returns is customer-written text running inside our agent's trust boundary, so it is also a prompt-injection channel.
**What it logs:** one line per call to `access.log` next to the server — caller `client_id`, tool, full arguments (ticket ids) and outcome, with no rotation or retention limit; behind our gateway it only ever sees the gateway's identity, so the real caller is recorded only in `week9/evidence/gateway_audit.log`.
**What a stolen token could do:** `dev-ticket-token` is a static bearer with `tickets:read` + `tickets:escalations`, no expiry, no audience or IP binding; whoever holds it can walk the whole TCK-0000…TCK-9999 id space (malformed and missing ids get different errors, which confirms which ones exist) and harvest every customer's contact details and escalation notes.
**Ship or don't:** ship only behind the gateway (`week9/gateway.py`), with short-lived per-caller scoped tokens, `contact_email` stripped and the static dev token rotated out; straight from the agent with today's token — don't ship.
